# ADR-009: 답변 코드 타입 검사 결과는 자동 수정하지 않고 출처 문서와 비교해 경고한다

## 메타

- **ADR ID**: ADR-009
- **상태**: 승인
- **날짜**: 2026-10-18
- **작성자**: 김아진
- **영향 범위**: Backend / Frontend
- **태그**: 유지보수 / 비용
- **관련 ADR**: ADR-003, ADR-007
- **링크**: `apps/web/src/lib/verify.ts`, `apps/web/src/lib/graph/nodes/verify.ts`, `scripts/verify-docs.ts`, `scripts/eval-verify.ts`

---

## 1) 배경 (Context)

- **문제**: 답변에 포함된 TypeScript 코드가 현재 패키지에 존재하지 않는 API나 잘못된 시그니처를 사용해도 사용자가 알 수 없다. generate 뒤에 `verify` 노드를 두고, 답변 코드를 실제 `@langchain/*`·`langchain`·`deepagents` 타입 정의로 타입 검사해 패키지 API 관련 에러만 판정한다 (판정 대상 에러 코드 10종). 이 ADR은 판정된 에러를 어떻게 처리하고 어떻게 분류하는지에 대한 결정이다.
- **제약**
    - 근거 문서 자체가 현재 타입 정의와 맞지 않는 경우가 많다. 공식 문서 예시 1,873블록 중 136블록(7.3%, 36페이지)에서 판정 대상 에러가 발생한다 (2026-10-17, `verify-docs`). 수동 확인 결과 대부분 문서와 타입 정의의 불일치이다 (`MemoryStore` → `InMemoryStore`, `createAgent`의 `prompt` → `systemPrompt`, deepagents `serverInfo`·`workingDirectory` 등).
    - 따라서 답변 코드의 에러는 "답변이 잘못 만든 코드"와 "문서 예시를 그대로 옮긴 코드" 두 경우가 섞인다. 후자는 답변이 근거 문서를 충실히 따른 결과이다.
    - LLM 호출은 Gemini 무료 티어 한도를 공유하며, 질문당 이미 3~10회 호출한다 (ADR-007).
    - 문서 원본(`data/pages.json`)은 저장소에 포함되지 않아 배포 환경에서 읽을 수 없다. 런타임에 접근 가능한 문서는 DB의 청크뿐이다.
    - 청크는 1,500자 / 150자 overlap으로 분할되어 코드 블록이 청크 경계에서 잘린다. 전체 3,049청크 중 코드 펜스(```) 수가 홀수인 청크가 929개이며, 이 청크에서는 잘린 코드 블록이 추출되지 않는다 (2026-10-18).
- **목표**: 답변 코드의 API 에러를 사용자에게 알리되, 답변의 오류와 문서의 오류를 구분해 표시할 것. LLM 호출을 늘리지 않을 것
- **비목표**: 답변 코드의 자동 수정, 문서 예시 자체의 오류 보고

## 2) 고려한 선택지 (Options)

**판정된 에러의 처리**

- 옵션 A: 자동 수정 (에러 내용을 LLM에 전달해 답변 재생성)
    - 장점: 사용자가 바로 실행 가능한 코드를 받을 가능성이 높음
    - 단점/리스크: 에러가 있는 답변마다 LLM 호출 증가. 문서 예시에서 비롯된 에러를 고치면 답변이 근거 문서와 달라져 출처 인용과 어긋남. 수정 결과의 재검증 반복 필요
- 옵션 B: 경고만 표시 (에러 구분 없음)
    - 장점: LLM 호출 증가 없음, 구현 단순
    - 단점/리스크: 문서를 그대로 옮긴 경우에도 답변 오류로 보여 답변 신뢰도를 과도하게 낮춤
- 옵션 C: 경고 + 출처 비교 (에러 코드와 API 이름으로 출처 문서 예시의 에러와 비교해 "출처에도 있음 / 출처에 없음"으로 구분)
    - 장점: LLM 호출 증가 없음. 답변 오류와 문서 오류를 구분해 각각 다른 안내 가능
    - 단점/리스크: 비교 대상 문서 코드의 범위에 따라 분류 정확도가 달라짐

**출처 비교의 대상 (옵션 C 채택 시)**

- 옵션 C-1: 답변에 사용된 출처 청크의 코드 블록을 런타임에 검사
    - 장점: 답변 근거와 정확히 같은 범위로 비교. 추가 데이터 파일 불필요
    - 단점/리스크: 청크 경계에서 잘린 코드 블록이 추출되지 않아 "출처에 없음"으로 잘못 분류됨. 답변에 에러가 있을 때마다 출처 코드 타입 검사 비용 발생
- 옵션 C-2: 출처 페이지 전체의 판정 에러 키(`에러 코드:API 이름`)를 미리 계산해 파일로 포함하고, 런타임에는 출처 URL로 조회
    - 장점: 코드 블록 분할의 영향 없음. 런타임 출처 검사 비용 없음. 파일 크기가 작음 (36페이지분)
    - 단점/리스크: 같은 페이지의 다른 예시에 있는 에러도 "출처에도 있음"으로 분류됨. 문서를 다시 수집하면 파일을 다시 생성해야 함
- 옵션 C-3: 코드 블록이 잘리지 않도록 재청킹
    - 장점: 근본 해결
    - 단점/리스크: 3,049청크 재임베딩에 임베딩 일일 한도(약 1,000건)로 수일 소요, 검색 품질 재측정 필요

## 3) 결정 (Decision)

- 최종 선택: 옵션 C, 출처 비교 대상은 옵션 C-2
- 결정 이유(Trade-off)
    - 문서 예시의 7.3%가 이미 타입 정의와 맞지 않으므로, 에러를 일괄 수정(A)하면 근거 문서와 다른 코드를 근거 인용과 함께 제시하게 된다. 일괄 경고(B)는 문서를 충실히 따른 답변까지 오류로 표시한다. 출처 비교(C)는 LLM 호출 없이 두 경우를 구분한다.
    - 청크 단위 비교(C-1)는 코드가 있는 청크의 상당수에서 코드 블록이 잘려 있어 체계적으로 "출처에 없음" 쪽으로 기운다. 페이지 단위 비교(C-2)는 같은 페이지의 다른 예시까지 포함하는 과대 귀속이 있으나, 같은 페이지의 예시에 같은 API 에러가 있다면 문서가 옛 API를 쓰고 있다는 안내는 여전히 유효하다고 판단한다. 재청킹(C-3)은 비용 대비 효과가 이 기능 하나에 한정된다.
    - 자동 수정(`fix` 노드)은 "출처에 없음" 비율을 측정한 뒤 근거가 있을 때 해당 경우에 한정해 검토한다.

## 4) 결과/영향 (Consequences)

- 긍정적 영향
    - 답변 아래에 통과 / "문서에 없는 API를 쓴 코드일 수 있음"(경고) / "문서 예시도 현재 패키지 타입과 맞지 않음"(안내)을 구분해 표시한다. 검사 결과는 답변 메시지에 저장되어 대화를 다시 불러와도 표시된다.
    - LLM 호출 수는 변하지 않는다. 런타임 타입 검사는 답변 코드에만 수행한다.
- 부정적 영향/부채
    - 문서를 다시 수집하면 `pnpm --filter scripts verify-docs -- --write`로 `apps/web/src/lib/source-errors.json`을 다시 생성해야 한다. 생성하지 않으면 새 문서의 에러가 "출처에 없음"으로 분류된다.
    - 타입 검사는 동기 실행이므로 그래프 시간 제한(`AbortSignal`)으로 중단되지 않는다. 콜드 요청에서 첫 검사가 2.4초 걸렸다 (2026-10-17, Vercel 프리뷰).
- 추후 작업(TODO)
    - 평가 문항을 늘려 "출처에 없음" 사례를 수집하고 `fix` 노드 도입 여부를 판단한다.
    - 문서 변경 추적(plan.md Phase 10)에 `source-errors.json` 재생성을 포함한다.

## 5) 검증/롤백 (Validation / Rollback)

- 검증 방법: `pnpm --filter scripts eval-verify` (검색 품질 평가셋 중 구현 방법을 묻는 20문항, classify → research 병렬 → generate → 코드 검증, gemini-3.1-flash-lite·일부 다음 모델 전환, 2026-10-18). 두 비교 방식은 같은 답변으로 판정했다.

| 항목 | C-1 청크 비교 | C-2 페이지 비교 |
|---|---:|---:|
| TS 코드가 있는 답변 | 20/20 | 20/20 |
| 판정 에러가 있는 답변 | 2/20 | 2/20 |
| 출처에도 있음 / 출처에 없음 | 0 / 2 | 2 / 0 |

- 판정 에러 2건(`state.authenticated` TS2339, `trimMessages`의 `tokenCounter` 누락 TS2345)을 수동 확인한 결과 모두 실제 타입 에러이며, 두 답변 모두 출처 문서 예시(context-engineering, add-memory)를 그대로 옮긴 코드였다. 페이지 비교의 분류가 맞고, 청크 비교는 두 문서 예시가 청크 경계에서 잘려 있어 오분류했다.
- 이번 표본에서 답변이 만든 API 에러("출처에 없음")는 0건이다. 표본이 작아 `fix` 노드 도입 근거로는 부족하다.
- 롤백 전략: `verifyAnswer`가 출처 URL 대신 출처 청크 본문을 받아 검사하도록 되돌린다 (C-1). 경고 표시 자체를 끄려면 그래프에서 `verify` 노드를 제거한다.
