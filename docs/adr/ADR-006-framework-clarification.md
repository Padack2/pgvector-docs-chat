# ADR-006: 대상 프레임워크가 불명확한 질문은 사용자 확인 후 해당 문서로 검색 범위 제한

## 메타

- **ADR ID**: ADR-006
- **상태**: 승인
- **날짜**: 2026-10-09
- **작성자**: 김아진
- **영향 범위**: Backend / Frontend
- **태그**: 성능 / 비용
- **관련 ADR**: ADR-005 (interrupt 재개에 필요한 체크포인트 저장)
- **링크**: plan.md Phase 6, `apps/web/src/lib/graph/nodes/classify.ts`, `apps/web/src/lib/graph/nodes/clarify.ts`, `apps/web/src/lib/db/pgvector.ts`, `scripts/eval-clarify.ts`

---

## 1) 배경 (Context)

- **문제**: 문서는 LangChain(createAgent·미들웨어), LangGraph(StateGraph), Deep Agents(createDeepAgent)로 구분되나, 메모리·스트리밍·human-in-the-loop·서브에이전트 등 동일 주제가 프레임워크별로 별도 문서화되어 있다. 검색 평가셋에서도 해당 유형의 질문은 정답 페이지가 복수의 프레임워크에 분포한다. "메모리는 어떻게 써?"와 같이 대상 프레임워크가 명시되지 않은 질문은 여러 프레임워크의 청크가 함께 검색되며, 그 결과 서로 다른 API(`createAgent`의 checkpointer 옵션, `StateGraph.compile` 등)가 하나의 답변에 혼재한다.
- **제약**
    - Gemini 무료 티어를 사용하므로 질문당 LLM 호출 수를 늘리기 어렵다 (gemini-3.8-flash 일일 20요청).
    - 확인 질문은 응답 시간을 늘리고 사용자 경험을 저하시킨다. 프레임워크가 명시되었거나 API 이름으로 추론 가능한 질문에는 확인 질문을 하지 않아야 한다.
    - 그래프 실행을 중단 후 재개하려면 실행 상태의 영속화가 필요하다 (ADR-005).
- **목표**
    - 답변이 프레임워크에 따라 달라지면서 판단 근거가 없는 질문에 한해 대상 프레임워크를 확인하고, 선택된 프레임워크 문서를 근거로 답변한다.
    - 질문당 LLM 호출 수를 유지한다.
- **비목표**: 프레임워크가 명시된 질문의 검색 범위 제한 (해당 질문은 검색어에 프레임워크 이름이 포함된다)

## 2) 고려한 선택지 (Options)

- 옵션 A: 현행 유지 (전체 문서 대상 검색)
    - 장점: 변경 사항 없음, 사용자 확인 단계 없음
    - 단점/리스크: 여러 프레임워크의 API가 혼재된 답변이 계속 발생한다.
- 옵션 B: classify가 대상 프레임워크를 추정하여 확인 없이 검색 범위를 제한
    - 장점: 사용자 입력 없이 단일 응답으로 처리된다.
    - 단점/리스크: 판단 근거가 없는 질문에서 추정이 틀리면 정답 문서 전체가 검색 범위에서 제외된다. 재검색(rewrite) 역시 동일 범위 내에서 수행되므로 복구 수단이 없다.
- 옵션 C: 확인 없이 후보 프레임워크별로 각각 검색하여 프레임워크별 답변을 함께 제공
    - 장점: 사용자 입력 없이 모든 경우를 제시한다.
    - 단점/리스크: 후보 수에 비례해 컨텍스트와 답변 길이가 증가하며, 사용자가 해당 사례를 직접 선별해야 한다.
- 옵션 D: 사용자 확인 후, 선택된 프레임워크 이름을 검색어에 추가
    - 장점: 검색 쿼리 구조 변경 없음
    - 단점/리스크: 임베딩을 해당 프레임워크 방향으로 편향시킬 뿐 범위를 제한하지 않으므로, 동일 주제의 타 프레임워크 청크가 포함될 수 있다.
- 옵션 E: 사용자 확인 후, 선택된 프레임워크 문서로 검색 범위를 제한 (`source_url` 경로 필터)
    - 장점: 선택되지 않은 프레임워크의 청크가 확실히 제외된다. 범위를 사용자가 직접 지정하므로 B 대비 정답 누락 위험이 낮다.
    - 단점/리스크: 답변 전 사용자 선택 단계가 추가된다. HNSW 인덱스는 후보를 먼저 선정한 뒤 WHERE 조건을 적용하므로, 필터 적용 시 결과가 k개 미만으로 반환될 수 있다.

## 3) 결정 (Decision)

- 최종 선택: 옵션 E
    - classify가 분류·검색어와 함께 "해당 가능한 프레임워크 후보"를 동일 호출에서 출력한다. 판단 근거가 없는 경우에만 후보를 출력하며, 불확실한 경우에는 빈 배열(확인 생략)을 출력한다.
    - 후보가 2개 이상이면 `clarify` 노드에서 `interrupt()`로 실행을 중단하고 선택지(후보 프레임워크 + "구분 없이 찾기")를 전달한다. `Command({ resume })`로 재개 시 선택값을 상태에 저장한다.
    - 검색 범위 필터는 사용자가 프레임워크를 선택한 경우에만 적용하며, 필터 검색에 한해 `hnsw.iterative_scan`을 활성화하여 결과 수 부족을 방지한다.
- 결정 이유(Trade-off)
    - 추정 오류 시 복구가 불가능한 B 대신, 선택 단계가 추가되는 E를 채택한다. 확인 조건을 좁게 설정하여 그 비용이 불명확한 질문에만 발생하도록 한다.
    - 범위를 명시적으로 제한하는 E가 검색어만 조정하는 D보다 혼재 방지 효과가 확실하다.
    - 후보 판단을 classify의 출력 필드로 통합하여 LLM 호출 수를 유지한다.
    - 자유 입력은 프레임워크로 변환하는 데 추가 LLM 호출이 필요하므로 제공하지 않고, "구분 없이 찾기" 선택지로 기존 동작(A)을 선택할 수 있게 한다.
    - `interrupt` 후 재개 시 해당 노드가 처음부터 재실행되므로, 확인 단계는 부수 효과가 없는 별도 노드(`clarify`)로 분리한다. classify 내부에서 중단할 경우 재개 시 LLM이 재호출된다.

## 4) 결과/영향 (Consequences)

- 긍정적 영향: 불명확한 질문은 선택된 프레임워크 문서만을 근거로 답변한다. 중단된 질문은 체크포인트에 보존되어 새로고침 후에도 선택지가 다시 표시되며, 이어서 진행할 수 있다.
- 부정적 영향/부채
    - 확인 여부 판단의 품질이 모델에 크게 의존한다. 23문항(확인 필요 10, 확인 불필요 13 — 앞선 대화에 단서가 있는 후속 질문 3 포함) 평가 결과, gemini-3.5-flash-lite는 20/23(recall 7/10, precision 7/7), 로컬 qwen2.5:7b는 14/23(recall 1/10)이다.
    - 필터는 `.../javascript/<framework>/` 경로 기준이므로, 프레임워크 공통 개념 문서(`concepts/memory` 등)는 필터 적용 시 검색 대상에서 제외된다.
    - classify 출력 필드 증가로 프롬프트가 길어졌다. 출력 항목을 추가로 늘릴 경우(예: Phase 7의 하위 질문) 확인 여부 판단 품질을 재측정해야 한다.
    - `hnsw.iterative_scan`은 pgvector 0.8 이상에서만 동작한다.
- 추후 작업(TODO)
    - 기본 모델(gemini-3.8-flash) 기준 확인 여부 판단 품질 측정
    - 필터 범위에 `concepts/` 문서 포함 여부 검토

## 5) 검증/롤백 (Validation / Rollback)

- 검증 방법
    - `pnpm --filter scripts eval-clarify`: 확인이 필요한 질문의 확인 비율(recall)과, 확인한 질문 중 실제로 필요했던 비율(precision). 불필요한 확인은 사용자 경험을 저하시키므로 precision을 우선하며, 이를 위해 classify 프롬프트에 "확실하지 않으면 확인하지 않는다"는 기준을 명시한다.
    - 필터 적용 검색 결과에 타 프레임워크 청크가 포함되지 않고, 결과 수가 k개 미만으로 줄지 않는지 확인
    - 새로고침 후에도 중단된 질문과 선택지가 표시되고, 선택 시 이어서 답변하는지 확인
- 롤백 전략: 그래프에서 classify → clarify 분기를 제거하고 항상 retrieve로 진행한다 (옵션 A). classify의 후보 필드는 남더라도 사용되지 않는다.
