# ADR-003: LLM 호출 실패 시 동일 모델 재시도 대신 후순위 모델로 즉시 전환

## 1) 배경 (Context)

- **문제**: 2026-10-09 Gemini 호출이 다음 세 가지 유형으로 실패하여 답변이 생성되지 않았다.
    - **사용 한도 초과 (429)**: gemini-3.8-flash 무료 티어는 일일 20요청·분당 5요청으로 제한된다 (429 응답의 quotaId로 확인). 질문 1건당 LLM을 3~9회 호출하므로 소수의 질문으로 일일 한도가 소진된다.
    - **무응답 정지**: gemini-3.8-flash가 오류 없이 응답을 멈추어 화면이 대기 상태로 유지되었다.
    - **일시적 과부하 (503)**: gemini-3.5-flash가 간헐적으로 503(high demand)을 반환했다.
- **제약**
    - 무료 티어를 유지한다 (유료 전환 시 전체 사용량이 과금되므로 당분간 유지, 2026-10-07 결정).
    - Vercel 함수 최대 실행 시간은 60초이며, 그래프 전체 실행은 50초로 제한한다. 이 시간 내에 여러 노드(classify, grade, rewrite, generate)의 LLM 호출이 모두 완료되어야 한다.
    - 배포 환경에는 로컬 모델(Ollama)을 사용할 수 없다.
- **목표**
    - 단일 모델의 한도 초과·무응답 상황에서도 답변을 제공한다.
    - 실패 대기로 인해 50초 제한을 초과하지 않도록 한다.
- **비목표**: 장애 상황에서의 답변 품질 동일성 유지 (경량 모델 전환에 따른 품질 저하는 허용한다)

## 2) 고려한 선택지 (Options)

- 옵션 A: 기본 동작 유지 (동일 모델 재시도)
    - 장점: 코드 변경 없음, 답변 모델이 일정하다.
    - 단점/리스크: 세 가지 실패 유형 중 어느 것도 해결하지 못한다. LangChain 기본 설정은 동일 모델로 최대 6회 재시도하나(`@langchain/core` 1.2.13 `AsyncCaller`), 일일 한도 소진은 재시도로 해소되지 않으며, 무응답 정지는 오류가 발생하지 않아 재시도 자체가 수행되지 않는다. 503은 재시도로 해소될 수 있으나 대기 시간이 50초 제한을 소모한다.
- 옵션 B: 유료 티어 전환
    - 장점: 사용 한도 문제가 해소된다.
    - 단점/리스크: 무료 티어 유지 결정과 상충한다. 무응답 정지와 503은 해소되지 않는다.
- 옵션 C: 모델 우선순위 목록을 두고, 실패 시 동일 모델 재시도 없이 후순위 모델로 즉시 전환
    - 호출별 시간 제한을 적용한다 (구조화 출력 15초, 답변 생성 30초). 무응답 정지를 실패로 판정하여 전환하기 위함이다.
    - 실패한 모델은 1분간 제외한다. 이후 노드에서 동일 모델의 시간 제한을 반복해서 기다리지 않기 위함이다.
    - 장점: 세 가지 실패 유형을 단일 경로로 처리한다. 무료 한도가 모델별로 부여되므로 가용 요청 수가 늘어난다.
    - 단점/리스크: 응답 모델에 따라 답변 품질이 달라진다. 모델 목록을 직접 관리해야 한다 (gemini-2.0-flash·2.5-flash는 신규 사용자에게 404 반환).
- 옵션 D: LangChain `Runnable.withFallbacks`로 모델 목록 구성
    - 장점: 별도 구현 없이 공식 API로 후순위 모델 전환이 가능하다.
    - 단점/리스크: 호출마다 첫 번째 모델부터 순차 시도하며, 실패한 모델을 제외하는 상태 관리 기능이 없다 (`@langchain/core` 1.2.13 `RunnableWithFallbacks`). 정지된 모델이 있을 경우 노드마다 시간 제한만큼 대기하게 되어 50초 제한을 초과할 가능성이 높다.

## 3) 결정 (Decision)

- 최종 선택: 옵션 C. 우선순위는 `GEMINI_MODEL`(기본 gemini-3.8-flash) → gemini-3.5-flash → gemini-3.1-flash-lite이며, 동일 모델 재시도(`maxRetries`)는 0으로 비활성화한다.
- 결정 이유(Trade-off)
    - 한도 소진과 무응답 정지는 동일 모델에서 대기로 해소되지 않으며, 50초 제한상 재시도 대기에 할애할 시간도 없다. 따라서 실패는 대기가 아닌 모델 전환으로 대응한다.
    - 후순위 모델 전환 방식 중 `withFallbacks`(D)는 실패 모델 제외 기능이 없으므로, 해당 상태를 직접 관리하는 C를 채택한다.
    - 경량 모델 전환에 따른 품질 저하는 답변 실패보다 수용 가능한 것으로 판단한다.

## 4) 결과/영향 (Consequences)

- 긍정적 영향: 단일 모델의 한도 초과·정지 상황에서도 답변이 생성된다. 노드의 LLM 호출이 `invokeChat` / `invokeStructured` 두 함수로 일원화된다.
- 부정적 영향/부채
    - 동일한 질문이라도 응답 모델에 따라 결과가 달라질 수 있다. 응답 모델은 화면에 표시되지 않으며 서버 로그(`console.warn`)에만 기록된다.
    - LLM을 호출하는 평가(eval-clarify 등)도 의도와 다른 모델로 수행될 수 있으므로, 평가 결과에 실제 수행 모델을 함께 기록해야 한다.
    - 실패 모델 제외 상태가 모듈 변수에 저장되므로 서버리스 인스턴스별로 독립 관리되며, 신규 인스턴스 기동 시 초기화된다. 이 경우 신규 인스턴스는 정지된 모델의 시간 제한을 다시 대기할 수 있다.
    - 모든 모델이 실패할 경우 시간 제한만큼 대기한 후에 오류가 반환된다 (최악의 경우 노드 1개에서 모델 3개 × 15초 소요).
    - 로컬 개발용 Ollama는 단일 모델로 동작하며 시간 제한이 적용되지 않는다.

## 5) 검증/롤백 (Validation / Rollback)

- 검증 방법: 주 모델이 한도 초과 또는 시간 초과로 실패할 때 서버 로그에 `LLM <모델> failed, trying next model`이 기록되고, 후순위 모델로 답변이 생성되는지 확인한다.
- 롤백 전략: `FALLBACK_MODELS`를 비우고 시간 제한을 제거하여 `GEMINI_MODEL` 단일 모델로 운영한다 (옵션 A).
