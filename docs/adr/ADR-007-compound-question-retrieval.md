# ADR-007: 복합 질문은 classify 단계에서 하위 질문으로 분해하여 개별 검색

## 메타

- **ADR ID**: ADR-007
- **상태**: 승인
- **날짜**: 2026-10-10
- **작성자**: 김아진
- **영향 범위**: Backend
- **태그**: 성능 / 비용
- **관련 ADR**:
- **링크**: plan.md Phase 7, `scripts/eval-compound.ts`, `scripts/eval/compound-questions.json`

## 1) 배경 (Context)

- **문제**: "checkpointer와 store는 뭐가 다르고 각각 언제 써?"와 같이 복수의 주제를 묻는 질문은, 단일 검색어로 상위 5청크를 조회할 경우 한 주제의 청크가 결과를 독점하여 다른 주제의 근거가 누락된다. 복합 질문 10개(하위 주제 2개씩, 두 주제가 서로 다른 페이지에 위치하도록 구성한 평가셋)로 측정한 결과, 모든 하위 주제의 정답 섹션이 컨텍스트에 포함된 질문은 **2/10**, 하위 주제 단위로는 **12/20**이었다 (2회 측정 모두 동일 수치, 누락 질문은 실행마다 일부 상이). 일례로 "토큰 스트리밍 + 노드 단위 테스트" 질문은 5청크 전부가 `streaming#LLM tokens` 섹션이었다. 단일 주제 질문의 검색 성능은 Hit@5 98%로 문제가 없다.
- **제약**
    - Gemini 무료 티어를 사용하므로 LLM 호출 수가 곧 사용 한도다 (gemini-3.8-flash 일일 20요청·분당 5요청). 현재 질문당 LLM 호출은 3~9회다.
    - 컨텍스트가 길어지면 generate 프롬프트가 커지고, 관련성이 낮은 청크가 포함되어 답변 품질이 저하될 수 있다.
- **목표**
    - 복합 질문에서 각 하위 주제의 정답 섹션이 컨텍스트에 포함되도록 한다.
    - 질문당 LLM 호출 수를 유지한다.
- **비목표**
    - 단일 주제 질문의 검색 품질 개선 (현재 수준으로 충분)
    - 하이브리드 검색(키워드+벡터) 도입 (주제 간 검색 결과 경합이라는 본 문제와 무관)

## 2) 고려한 선택지 (Options)

LLM이 필요 없는 B·C는 기준선 1차 측정에서 classify가 생성한 검색어를 동일하게 사용하여 측정했다 (상위 30청크에서 선별).

| 방법 | 전체 하위 주제 포함 질문 | 포함된 하위 주제 |
|---|---|---|
| 기준선 (상위 5청크) | 2/10 | 12/20 |
| C: 상위 10청크 | 3/10 | 13/20 |
| B1: 동일 섹션 청크 1개만 유지, 5청크 | 2/10 | 12/20 |
| B2: MMR λ=0.7, 5청크 | 2/10 | 11/20 |
| B2: MMR λ=0.5, 5청크 | 2/10 | 10/20 |
| B1+C: 동일 섹션 1개만 유지, 10청크 | 4/10 | 14/20 |

- 옵션 A: 질문을 하위 질문 1~3개로 분해하여 하위 질문별로 검색한 뒤 결과를 병합 (Phase 7 원안)
    - 장점: 하위 주제마다 독립된 검색어를 사용하므로 주제 간 경합이 발생하지 않는다. 하위 질문 생성을 classify의 출력 필드로 통합하면 LLM 호출 수가 증가하지 않는다 (classify는 이미 질문을 독립 질문으로 재작성하고 있다). 단일 주제 질문은 하위 질문 1개로 처리되어 기존과 동일한 경로로 실행된다.
    - 단점/리스크: 하위 질문 수만큼 임베딩 호출과 DB 검색이 증가한다. 분해 품질이 모델 성능에 의존한다 (불필요한 분해 또는 분해 누락).
    - 사전 측정: classify에 하위 질문 출력 필드를 추가하고, 1회 호출의 출력(searchQuery, subQueries)으로 기준선과 분해를 함께 측정했다 (검색 단계, 2회 측정). 하위 질문별 상위 10청크를 순위별로 교차 병합하고 동일 청크는 1개만 유지했다.

| 방법 | 전체 하위 주제 포함 질문 (1차 / 2차) | 포함된 하위 주제 (1차 / 2차) |
|---|---|---|
| 기준선 5청크 | 3/10 / 2/10 | 12/20 / 11/20 |
| 기준선 8청크 | 3/10 / 3/10 | 13/20 / 12/20 |
| 분해 5청크 | 4/10 / 6/10 | 14/20 / 16/20 |
| 분해 8청크 | 7/10 / 8/10 | 17/20 / 18/20 |
| 분해 8청크 + 섹션 중복 제거 | 8/10 / 8/10 | 18/20 / 18/20 |
| 분해 10청크 | 8/10 / 8/10 | 18/20 / 18/20 |

- 옵션 B1: 동일 섹션의 청크를 1개만 유지
    - 장점: LLM·임베딩 호출 추가 없음, 구현 범위가 작다.
    - 단점/리스크: 단독 적용 시 효과가 없었다 (12→12). C와 병행할 때만 1개 하위 주제가 추가로 포함되었다 (13→14).
- 옵션 B2: MMR (질문과의 유사도와 기선정 청크와의 유사도를 함께 반영하여 선별)
    - 장점: LLM 호출 추가 없음
    - 단점/리스크: 기준선보다 성능이 하락했다 (12→11, 10). 기준선에서 포함되던 `tracing` 하위 주제도 누락되었다. 원인은 분석하지 않았다.
- 옵션 C: 검색 개수를 5에서 10으로 확대
    - 장점: 설정값 1개만 변경
    - 단점/리스크: 개선 폭이 하위 주제 1개에 그쳤다 (12→13). generate 프롬프트 길이가 2배가 되며, 상위 10위 내에도 없는 하위 주제 7개(`long-term memory`, `fallbacks`, `trajectory evals`, `visualization` 등)는 여전히 누락된다.

## 3) 결정 (Decision)

- 최종 선택: 옵션 A. 하위 질문은 classify가 함께 출력한다. 하위 질문별 결과는 순위별로 교차 병합하고, 동일 섹션은 1개만 유지하여(B1) 상한 8청크로 컨텍스트를 구성한다. B2·C는 채택하지 않는다.
- 결정 이유(Trade-off): LLM이 필요 없는 방법을 모두 결합해도(B1+C) 4/10에 그쳤으며, 누락된 하위 주제 대부분은 단일 검색어로는 상위 10위 내에 포함되지 않았다. 따라서 검색어 자체를 주제별로 분리해야 한다. 사전 측정에서 분해(8청크, 섹션 중복 제거)는 2회 모두 8/10으로, 동일 호출의 기준선(3/10, 2/10) 대비 5~6문항 개선되었다. 분해 시 5청크 상한은 하위 주제별 근거를 모두 담기에 부족하고(4/10, 6/10), 섹션 중복 제거를 적용한 8청크는 10청크와 동일한 결과를 더 짧은 컨텍스트로 얻는다. 분해를 별도 노드로 구성하면 질문당 LLM 호출이 1회 증가하여 무료 티어 한도에 직접적인 영향을 주므로, 이미 질문 재작성을 수행하는 classify에 출력 필드를 추가한다.

## 4) 결과/영향 (Consequences)

- 긍정적 영향: 복합 질문에서 하위 주제별 근거를 확보할 수 있다. 질문당 LLM 호출 수는 유지된다.
- 부정적 영향/부채
    - classify 출력 항목이 늘어나 소형 모델에서 분류·확인 여부 판단 품질이 저하될 수 있다. eval-clarify로 재측정한다.
    - 하위 질문 수만큼 임베딩 호출이 증가한다 (임베딩 일일 한도 약 1,000건을 질문 임베딩과 공유).
    - 답변 컨텍스트가 5청크에서 최대 8청크로 늘어 generate 프롬프트가 길어진다.
    - classify 프롬프트와 출력이 늘어 응답 시간이 증가할 수 있다. 사전 측정 중 구조화 출력 시간 제한(15초) 초과가 여러 차례 발생했으나, 같은 시간대에 503 과부하도 함께 발생하여 프롬프트 증가의 영향은 분리되지 않았다.
- 추후 작업(TODO)
    - grade의 적용 단위 결정: 하위 질문별 평가(LLM 호출이 하위 질문 수만큼 증가)와 병합 결과 1회 평가(호출 수 유지, 부족한 하위 질문 식별 불가) 중 측정 후 결정

## 5) 검증/롤백 (Validation / Rollback)

- 검증 방법
    - `pnpm --filter scripts eval-compound`에서 그래프 적용 후에도 사전 측정 수준(분해 8청크 + 섹션 중복 제거, 8/10·18/20)이 유지되는지 확인
    - 단일 질문 평가(`pnpm --filter scripts eval`, Hit@5 98%)와 eval-clarify(확인 여부 판단) 결과가 하락하지 않는지 확인
    - 측정 시 유의 사항
        - 기준선 검색어 생성 모델이 혼재되어 있다. 1차는 3.8-flash 시간 초과·3.5-flash 503으로 대부분 3.1-flash-lite, 2차는 앞 6문항 3.8-flash·나머지 3.1-flash-lite가 생성했다 (3.5-flash는 일일 한도 소진). 분해 적용 후에도 동일 모델로 2회 이상 측정하여 비교한다.
        - 정답 섹션은 분해 결과 확인 전에 확정했다. 판정 기준은 "해당 섹션만으로 하위 주제에 답할 수 있으며, 질문이 지정한 프레임워크 범위 내일 것"이다 (`scripts/eval-compound.ts` 주석). 초기 목록의 범위가 좁아, 하위 주제별 집중 검색 상위 8개의 본문을 검토하여 21개 섹션을 추가했다 (기준선 하위 주제 10/20 → 12/20).
- 롤백 전략: classify의 하위 질문 출력을 사용하지 않고 `searchQuery` 단일 검색으로 되돌린다 (현행 방식).
