# ADR-012: 프레임워크 선호는 익명 쿠키 ID로 구분하고 되묻지 않고 적용한다

## 메타

- **ADR ID**: ADR-012
- **상태**: 승인
- **날짜**: 2026-10-22
- **작성자**: 김아진
- **영향 범위**: Backend / Frontend / Data
- **태그**: 개발자경험(DX) / 유지보수
- **관련 ADR**: ADR-005, ADR-006, ADR-010
- **링크**: `apps/web/src/lib/graph/nodes/clarify.ts`, `apps/web/src/lib/db/store.ts`, `apps/web/src/app/api/chat/route.ts`, `docs/schema.md`

---

## 1) 배경 (Context)

- **문제**: 애매한 질문에서 되묻기로 고른 프레임워크(ADR-006)는 그 대화의 체크포인트에만 남는다. 같은 사용자가 새 대화를 시작하면 매번 같은 선택지에 다시 답해야 한다. 대화 단위 상태(체크포인트)와 별도로 사용자 단위 기억이 필요하다.
- **제약**
    - 로그인은 비목표이다 (ADR-005). 사용자를 구분할 수단이 없다.
    - 기억을 적용하는 위치는 `clarify` 노드이다. 재개 시 노드가 처음부터 다시 실행되므로 `interrupt()` 앞에는 읽기만 둘 수 있다.
    - 저장소는 Neon 무료 플랜을 사용하며, 체크포인트 계정(`checkpoint_user`)은 자기 소유 스키마만 접근한다 (ADR-010).
    - Gemini 무료 티어 한도로 인해 LLM·임베딩 호출을 늘리지 않아야 한다.
- **목표**: 같은 브라우저에서 한 번 고른 프레임워크를 다음 대화의 애매한 질문에 적용하고, 사용자가 언제든 되묻기로 되돌릴 수 있을 것
- **비목표**: 기기 간 기억 공유, 프레임워크 외의 선호·대화 내용 기억, 로그인

## 2) 고려한 선택지 (Options)

### 사용자 식별

- 옵션 A: 서버가 발급하는 익명 UUID를 httpOnly 쿠키로 저장
    - 장점: 모든 요청(새 질문, 재개, 분기)에 자동으로 포함되어 클라이언트 요청 코드를 바꿀 필요가 없음. 페이지 스크립트에서 값을 읽을 수 없음. 서버가 형식을 검사하고 잘못된 값이면 새로 발급할 수 있음
    - 단점/리스크: 쿠키를 지우거나 다른 브라우저를 쓰면 기억이 사라짐. 같은 브라우저를 쓰는 사람끼리 기억을 공유함
- 옵션 B: 클라이언트가 만든 ID를 localStorage에 두고 요청 본문으로 전송
    - 장점: 서버 쪽 쿠키 처리가 없음
    - 단점/리스크: 요청을 보내는 모든 경로에 ID를 추가해야 함. 페이지 스크립트에서 값을 읽을 수 있음. 기억이 사라지는 조건은 옵션 A와 같음
- 옵션 C: 로그인 도입
    - 장점: 기기 간 공유, 사용자 구분이 정확함
    - 단점/리스크: 데모 서비스의 비목표(ADR-005)이며 인증 구현·개인정보 관리 부담이 기능 규모에 비해 큼

### 기억 적용 방식

- 옵션 1: 기억된 프레임워크가 이번 질문의 후보에 있으면 되묻지 않고 적용하고, 답변에 "기억된 선택 · 변경"을 표시
    - 장점: 반복 되묻기가 사라짐. 잘못 적용되면 "변경"으로 되묻기를 다시 받을 수 있음
    - 단점/리스크: 사용자가 이번에는 다른 프레임워크를 의도했어도 일단 기억된 값으로 답함
- 옵션 2: 계속 되묻되 기억된 프레임워크를 첫 선택지로 강조
    - 장점: 잘못 적용되는 경우가 없음
    - 단점/리스크: 매번 그래프가 멈추고 선택을 기다리므로 반복 입력을 줄이는 목표를 달성하지 못함

## 3) 결정 (Decision)

- 최종 선택: 사용자 식별은 옵션 A, 적용 방식은 옵션 1
- 결정 이유(Trade-off)
    - 식별: 기억이 사라지는 조건은 A와 B가 같고, A는 요청 경로를 바꾸지 않으며 스크립트에 노출되지 않는다. 기억 대상이 프레임워크 선호 하나뿐이라 쿠키 분실 시 손실은 되묻기 한 번이다.
    - 적용: 되묻기는 classify가 프레임워크 단서를 찾지 못한 경우에만 발생하므로(ADR-006), 같은 사용자가 이전에 고른 프레임워크가 의도와 일치할 가능성이 높다. 일치하지 않는 경우의 비용은 "변경" 한 번이며, 매번 멈추는 비용보다 작다고 판단했다.
    - 기억된 값이 이번 후보에 없으면 그 질문에 맞지 않으므로 기존처럼 되묻는다. "구분 없이 찾기"를 고르면 특정 프레임워크를 선호하지 않는다는 뜻이므로 기억을 지운다.
- 저장소: `PostgresStore`를 체크포인트와 같은 `langgraph` 스키마에 둔다. 체크포인트와 같은 계정·권한 절차를 따르며, 값이 프레임워크 이름 하나라 벡터 인덱스는 쓰지 않는다.

## 4) 결과/영향 (Consequences)

- 긍정적 영향
    - 체크포인트(대화 단위)와 Store(사용자 단위, namespace `["users", user_id]`)를 함께 사용하며, 추가 LLM·임베딩 호출이 없다.
    - 기억 적용 여부(`frameworkRemembered`)를 그래프 상태에 저장하므로, 다시 불러온 대화에서도 "기억된 선택" 표시가 유지된다.
- 부정적 영향/부채
    - 재개 요청과 "변경" 재실행은 항상 기억을 무시한다(`ignore_memory`). 재개 시 `clarify`가 처음부터 다시 실행되는데, 그사이 다른 탭에서 기억이 생기면 사용자의 선택 대신 기억이 적용되기 때문이다.
    - `PostgresStore`는 기존 Pool을 받지 않아 체크포인트와 별도의 커넥션 풀이 하나 더 생긴다.
    - Store 행은 대화가 아닌 사용자 단위이므로 `cleanup-threads`가 지우지 않는다. 쿠키가 사라진 사용자의 행은 남지만, 사용자당 1행이라 정리 대상에서 제외했다.
- 추후 작업(TODO): 로그인을 도입하면 익명 ID의 기억을 계정으로 옮기는 절차가 필요하다.

## 5) 검증/롤백 (Validation / Rollback)

- 검증 방법: 같은 쿠키로 두 번째 애매한 질문부터 되묻지 않고 기억이 적용되는지, 다른 쿠키·후보에 없는 선호·"변경"에서는 되묻는지, "구분 없이 찾기" 선택 시 기억이 지워지는지 확인한다.
- 롤백 전략: 그래프를 `store` 없이 컴파일하면 `clarify`가 Store를 조회하지 않아 기존 되묻기 동작으로 돌아간다. 테이블은 `langgraph.store`·`store_migrations`를 삭제한다. 대화 체크포인트에는 영향이 없다.
