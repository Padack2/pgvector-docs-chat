# ADR-001: 임베딩 모델은 gemini-embedding-001 (1536차원)으로 고정

## 메타

- **ADR ID**: ADR-001
- **상태**: 승인
- **날짜**: 2026-10-03
- **작성자**: 김아진
- **영향 범위**: Data / Backend
- **태그**: 성능 / 비용 / 유지보수
- **관련 ADR**:
- **링크**: https://ai.google.dev/gemini-api/docs/embeddings

---

## 1) 배경 (Context)

- **문제**: 스키마는 `VECTOR(1536)`으로 잡혀 있었지만 임베딩 모델은 정해지지 않았다. 임베딩 모델은 문서를 저장할 때와 질문을 검색할 때 같은 것을 써야 해서, 나중에 바꾸면 전체 재임베딩이 필요하다. 그래서 처음에 신중히 고정해야 한다.
- 같은 시기에 LLM은 로컬 개발용으로 Ollama 전환(`LLM_PROVIDER`)을 넣었기 때문에, 임베딩도 Ollama로 할 수 있는지가 함께 검토 대상이 됐다.
- **제약**
    - 배포는 Vercel(서버리스)이다. 질문 임베딩은 런타임에 일어나므로 Vercel에서 호출할 수 있는 모델이어야 한다.
    - pgvector HNSW 인덱스는 `vector` 타입 기준 최대 2000차원까지만 지원한다.
- **목표**: 배포 환경에서 동작하고, HNSW 인덱스를 그대로 쓰며, 품질 손실이 없는 모델·차원
- **비목표**: 멀티모달(이미지 등) 검색

## 2) 고려한 선택지 (Options)

- 옵션 A: Ollama 임베딩 (`nomic-embed-text` 768 등)
    - 장점: 무료, 한도 없음
    - 단점/리스크: Vercel에서 질문 임베딩 불가 → 배포 시 별도 GPU 서버 필요
- 옵션 B: `gemini-embedding-001` 기본 3072차원
    - 장점: 설정 없이 바로 사용, 정규화된 벡터 반환
    - 단점/리스크: 2000차원 초과로 `vector` HNSW 인덱스 불가 (`halfvec` 캐스팅 필요)
- 옵션 C: `gemini-embedding-001` + `outputDimensionality: 1536`
    - 장점: MRL 학습 모델이라 1536에서도 MTEB 점수가 3072와 동일(68.17), HNSW 인덱스 그대로 사용
    - 단점/리스크: 3072 미만은 정규화되지 않은 벡터 반환 → 직접 L2 정규화 필요
- 옵션 D: `gemini-embedding-2`
    - 장점: 최신, 입력 8192토큰
    - 단점/리스크: 멀티모달 장점은 텍스트 문서뿐인 이 프로젝트에서 불필요

## 3) 결정 (Decision)

- 최종 선택: 옵션 C — `gemini-embedding-001`, 1536차원
- 결정 이유(Trade-off): 배포 가능성(A 제외)과 인덱스 제약(B 제외)을 동시에 만족하면서 품질 손실이 없다. 대가는 정규화 코드 한 줄. 문서가 수백 청크 수준이라 768 대비 저장 공간 차이는 무의미하다.

## 4) 결과/영향 (Consequences)

- 긍정적 영향: LLM은 자유롭게 교체해도 DB 재구축이 필요 없다.
- 부정적 영향/부채: 임베딩 모델·차원을 바꾸면 전체 재임베딩 + `VECTOR(n)` 스키마 변경 필요.
- 추후 작업(TODO):
    - 모델명·차원·정규화를 한 곳에 두고 `scripts/embed.ts`와 `lib/db/pgvector.ts`가 공유
    - taskType 구분: 청크는 `RETRIEVAL_DOCUMENT`, 질문은 `RETRIEVAL_QUERY`
    - 입력 한도 2048토큰 → 청크 크기는 이보다 충분히 작게

## 5) 검증/롤백 (Validation / Rollback)

- 검증 방법: 2026-10-03 실제 호출로 1536차원 반환 및 L2 norm ≈ 0.70(비정규화) 확인. 저장 후 샘플 질문의 상위 5개 청크가 관련 내용인지 확인.
- 롤백 전략: 차원 변경 시 `doc_chunks` 비우고 `VECTOR(n)` 변경 후 재임베딩.
