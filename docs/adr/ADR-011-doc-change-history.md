# ADR-011: 문서 변경 이력은 바뀐 섹션의 전/후 본문과 함께 동기화 트랜잭션에서 기록하고, 요약은 별도 단계로 생성한다

## 메타

- **ADR ID**: ADR-011
- **상태**: 승인
- **날짜**: 2026-10-20
- **작성자**: 김아진
- **영향 범위**: Data / Infra
- **태그**: 비용 / 유지보수
- **관련 ADR**: ADR-002, ADR-003
- **링크**: `scripts/embed.ts`, `scripts/summarize-changes.ts`, `.github/workflows/sync-docs.yml`, `docs/schema.md`

---

## 1) 배경 (Context)

- **문제**: 증분 동기화(ADR-002)는 바뀐 페이지의 청크를 삭제 후 재삽입하므로, 동기화가 끝나면 어떤 문서가 어떻게 바뀌었는지 남지 않는다. 문서 갱신을 주기적으로 반영하려면 사용자에게 바뀐 내용을 요약해 보여주고, 이전 대화가 인용한 문서가 이후 바뀌었는지 알려야 한다. 이를 위해서는 변경 전 본문이 교체 전에 어딘가에 보존되어야 한다.
- **제약**
    - ADR-002의 비목표였던 주기적 자동 갱신을 이번에 도입한다. 크롤링·청킹·임베딩은 실행 시간이 길어 Vercel 함수 제한(60초) 안에 끝나지 않으므로 GitHub Actions 예약 실행으로 돌린다.
    - 임베딩 일일 한도(약 1,000건)와 LLM 무료 한도를 챗봇과 공유한다. 한 번의 실행에서 모든 변경을 처리하지 못할 수 있으며, 중단 후 다음 실행이 이어서 처리해야 한다 (ADR-002의 재실행 안전성 유지).
    - `embed_user`는 SELECT / INSERT / DELETE만 가능하다 (ADR-002). `doc_chunks`의 검색 쿼리는 현재 버전 청크만 있다고 가정한다.
- **목표**: 페이지별 추가·변경·삭제와 바뀐 섹션의 내용을 중복·누락 없이 기록하고, 이를 입력으로 페이지당 LLM 1회 요약을 생성할 것
- **비목표**: 청킹 파라미터 변경으로 인한 전체 재임베딩을 문서 변경과 구분하는 것

## 2) 고려한 선택지 (Options)

- 옵션 A: 이력에 페이지와 바뀐 섹션 경로만 기록하고, `embed.ts`가 청크를 교체하기 전에 LLM으로 요약해 함께 저장
    - 장점: 이력 테이블이 작음
    - 단점/리스크: 임베딩 트랜잭션 안에 LLM 호출이 들어가 LLM 실패·한도가 임베딩 진행을 막음. 요약이 실패하면 변경 전 본문이 이미 사라져 다시 요약할 수 없음. 요약 프롬프트를 고쳐도 과거 이력을 재요약할 수 없음
- 옵션 B: 이력에 바뀐 섹션의 전/후 본문을 기록하고(청크 교체와 같은 트랜잭션), 요약은 별도 스크립트가 요약이 없는 이력부터 생성
    - 장점: 임베딩과 요약의 실패가 서로 독립적이며, 둘 다 중단 후 이어서 처리 가능. 요약을 다시 생성할 수 있음. 페이지 교체와 이력 기록이 함께 커밋되므로 중복·누락 없음
    - 단점/리스크: 섹션 본문을 저장하므로 이력 크기가 커짐. 섹션 하나가 3만 자를 넘는 경우가 있어 요약 입력을 줄이는 처리가 필요
- 옵션 C: `doc_chunks`에 버전 열을 두고 이전 청크를 삭제하지 않고 보존
    - 장점: 전/후 비교에 별도 테이블 불필요
    - 단점/리스크: 검색 쿼리마다 현재 버전 조건이 필요하고 HNSW 인덱스에 이전 버전 벡터가 섞임. `embed_user`에 UPDATE 권한이 필요해 ADR-002의 권한 구성을 변경해야 함

## 3) 결정 (Decision)

- 최종 선택: 옵션 B
- 결정 이유(Trade-off): 변경 전 본문은 교체 후 복구할 수 없으므로, 요약 성공 여부와 무관하게 교체 시점에 확실히 남기는 것을 우선한다. 저장 공간 증가는 주 1회 동기화 규모(페이지 수십 개)에서 무료 티어 용량에 영향이 없는 수준으로 판단한다.
- 세부 사항
    - `doc_changes`에 페이지·변경 유형(`added`/`changed`/`removed`)·바뀐 섹션 목록(`sections` jsonb, 섹션 경로별 전/후 본문)·동기화 시각을 기록한다. 섹션은 청크 첫 줄의 섹션 경로로 묶어 비교한다.
    - 요약은 같은 행의 `summary` 열에 저장한다. 요약이 이력 행과 1:1이고, NULL이 미처리 표시를 겸한다. `embed_user`에는 `summary` 열의 UPDATE만 추가로 부여하고 나머지 열은 INSERT 전용으로 유지한다.
    - 한도 공유에 대응해 1회 실행당 임베딩 800청크, LLM 요약 30페이지의 상한을 두고 나머지는 다음 실행으로 넘긴다. 요약은 챗봇 기본 모델의 한도를 쓰지 않도록 `gemini-3.1-flash-lite`를 지정하며, 실패 시 기존 모델 자동 전환(ADR-003)을 따른다.
    - 요약 입력은 전/후 공통 앞뒤를 덜어낸 달라진 구간(앞뒤 300자 포함)만 사용하고, 3,000자를 넘으면 가운데를 생략한다.

## 4) 결과/영향 (Consequences)

- 긍정적 영향: 임베딩과 요약이 각각 상한·한도로 중단되어도 다음 실행에서 이어서 처리된다. "최근 문서 변경" 화면과 답변 출처의 "이후 변경됨" 표시가 이 이력을 사용한다.
- 부정적 영향/부채:
    - 청킹 파라미터를 바꾸면 전 페이지가 `changed`로 기록된다. 현재 대응은 해당 이력 행을 수동으로 삭제하는 것이다.
    - "이후 변경됨"은 페이지 단위로 판정하므로, 답변이 인용한 섹션이 아닌 다른 섹션만 바뀌어도 표시된다.
    - 이력은 삭제하지 않고 누적된다.
- 추후 작업(TODO): 이력이 누적되어 용량이 문제가 되면 오래된 이력의 `sections` 본문을 비우는 정리 작업을 추가한다.

## 5) 검증/롤백 (Validation / Rollback)

- 검증 방법
    - 변경 없는 재실행에서 이력이 생성되지 않고, 한 페이지의 섹션을 임시로 수정하면 해당 섹션의 전/후 본문을 담은 이력 1행이 생성되는지 운영 DB에서 확인한다.
    - 일일 한도로 중단된 동기화를 다시 실행해 이력의 중복·누락이 없는지 확인한다.
    - 요약 표본을 실제 문서 변경과 대조한다.
- 롤백 전략: `embed.ts`의 이력 INSERT와 Actions의 요약 단계를 제거한다. `doc_chunks`와 검색 경로는 변경되지 않았으므로 챗봇 동작에는 영향이 없다.
