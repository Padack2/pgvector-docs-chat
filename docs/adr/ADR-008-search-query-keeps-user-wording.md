# ADR-008: classify 검색어는 사용자 표현을 유지한다

## 메타

- **ADR ID**: ADR-008
- **상태**: 승인
- **날짜**: 2026-10-14
- **작성자**: 김아진
- **영향 범위**: Backend
- **태그**: 성능
- **관련 ADR**: ADR-006, ADR-007
- **링크**: `apps/web/src/lib/graph/nodes/classify.ts`

---

## 1) 배경 (Context)

- **문제**: 챗봇 경로의 단일 질문 검색 성능이 질문 원문 검색보다 낮다. 검색 품질 평가셋 50문항에서 원문 검색(`pnpm eval`)은 Hit@5 98%이나, classify가 작성한 검색어로 검색하면 정답 섹션 포함 질문이 43/50(86%)이다 (ADR-007 검증 절, 2026-10-14). 문항별로 확인한 결과 원인은 다음 두 가지이다.
    - 혼자서 이해되는 첫 질문도 재작성하면서, 질문에 단서가 없는 프레임워크 이름(주로 "LangGraph에서")을 덧붙인다. 50문항 중 앞 25문항에서 23건 발생했다.
    - "서버를 재시작하면 대화 기록이 다 날아가" 같은 증상 설명을 "~하는 방법"으로 바꾸어, 증상 단위로 작성된 Troubleshooting 섹션을 놓친다.
    - 하락은 상황 설명형 한국어 질문에 집중되며, API 이름·에러 메시지 질문에서는 발생하지 않는다.
- **제약**
    - classify는 검색어·하위 질문·프레임워크 후보를 LLM 호출 1회로 출력한다 (ADR-007). 호출 수를 늘리지 않는다.
    - 프레임워크 후보 출력은 되묻기 판단(ADR-006)에 사용되므로, 검색어 규칙 변경이 되묻기 판단에 영향을 줄 수 있다.
    - 평가셋 문구를 프롬프트 예시로 사용하지 않는다.
- **목표**: 챗봇 경로의 단일 질문 검색을 원문 검색 수준으로 회복하고, 복합 질문 분해 성능(8/10)을 유지할 것
- **비목표**: 후속 질문("그거 예시는?")의 재작성 방식 변경

## 2) 고려한 선택지 (Options)

- 옵션 A: classify 프롬프트에 "혼자서 이해되는 질문은 그대로 쓰고, 증상 표현을 유지하며, 단서 없이 프레임워크 이름을 붙이지 않는다" 규칙 추가
    - 장점: 코드 경로 변경 없음, LLM·임베딩 호출 수 동일
    - 단점/리스크: 모델이 규칙을 따르는 정도에 의존. 프레임워크 관련 규칙이 프레임워크 후보 출력(되묻기 판단)에 영향을 줄 수 있음
- 옵션 B: 대화의 첫 질문은 코드에서 원문을 검색어로 사용 (classify 출력 무시)
    - 장점: 결정적이며 첫 질문의 하락을 확실히 제거
    - 단점/리스크: 하위 질문은 여전히 classify가 작성하므로 분해된 질문에는 효과 없음. 첫 질문이 아니어도 혼자서 이해되는 질문에는 적용되지 않음
- 옵션 C: 원문과 classify 검색어로 각각 검색 후 병합
    - 장점: 두 검색어의 장점을 모두 확보
    - 단점/리스크: 임베딩 호출 2배 (일일 한도 약 1,000건 공유), 병합 대상 증가로 답변 컨텍스트 상한(8청크) 경쟁 심화

## 3) 결정 (Decision)

- 최종 선택: 옵션 A
- 결정 이유(Trade-off): 하락 원인이 재작성 규칙의 부재에 있으므로 규칙으로 직접 대응한다. 옵션 B는 하위 질문에 효과가 없고, 옵션 C는 무료 한도 안에서 임베딩 비용이 커진다. 되묻기 판단에 미치는 영향은 eval-clarify로 확인하고, 하락 시 롤백한다.

## 4) 결과/영향 (Consequences)

- 긍정적 영향: 단일 질문 검색이 원문 검색 수준으로 회복되었다. 단일 주제 질문의 불필요한 분할이 줄어 grade 호출이 감소한다.
- 부정적 영향/부채
    - 되묻기 precision이 하락했다. 수정 전 2회 모두 불필요한 되묻기가 없었으나(19/19·18/18), 수정 후 2회에 1·2건(21/23·22/24) 발생했다. 프레임워크 이름을 붙이지 않는 규칙에 따라 모델이 프레임워크를 단정하지 않는 쪽으로 기운 것으로 판단된다. 불필요하게 되물은 질문도 "구분 없이 찾기"를 선택하면 수정 전과 같은 경로로 답변되므로 답변 품질에는 영향이 없고, 사용자 입력이 1회 늘어난다.
    - 검색어가 원문과 완전히 같아지지는 않는다. 50문항 중 원문과 동일한 검색어는 18건이다.
- 추후 작업(TODO): 단일 질문의 그래프 경유 LLM 호출 측정(ADR-007 TODO)은 분할 감소 후 상태로 측정한다.

## 5) 검증/롤백 (Validation / Rollback)

- 검증 방법: 모두 gemini-3.1-flash-lite 고정. 수정 전 수치는 ADR-007 검증 절의 동일 조건 측정값이다.

| 평가 | 수정 전 | 수정 후 (2026-10-16) |
|---|---|---|
| 단일 질문 50문항, 검색만 (`eval-compound --single`) — 분해 8청크 + 섹션 중복 제거 | 44/50 · 45/50 | 49/50 |
| 〃 — 기준선 (classify 검색어 1개, 5청크) | 43/50 · 43/50 | 47/50 |
| 〃 — 하위 질문 2개 이상으로 분할된 질문 | 24/50 · 26/50 | 13/50 |
| 복합 질문 10문항, 그래프 경유 (`eval-compound --graph`) | 8/10 · 8/10 · 8/10 | 8/10 (18/20) |
| 되묻기 49문항 (`eval-clarify`) — 정확도 | 46/49 · 45/49 | 46/49 · 47/49 |
| 〃 — recall | 19/22 · 18/22 | 21/22 · 22/22 |
| 〃 — precision | 19/19 · 18/18 | 21/23 · 22/24 |

- 측정 시 유의 사항
    - 단일 질문과 복합 질문은 1회 측정이다. 단일 질문 측정 중 3회, 복합 질문 측정 중 1회 3.1-flash-lite 시간 초과가 발생하여 해당 호출은 대체 모델이 응답했다.
    - 단일 질문에서 남은 누락 1건(e05 `ContextOverflowError`)은 원문 검색에서도 상위 5개 밖인 문항이다.
    - 수정 후에도 단서 없는 프레임워크 이름이 붙은 검색어는 50문항 중 11건이다. 2026-10-14 부분 측정(앞 25문항, 503으로 중단)에서는 같은 구간이 23건에서 3건으로 감소했다.
    - 복합 질문은 10문항 모두 하위 질문 2개로 분할되어, 프레임워크 이름 규칙이 복합 질문 분해에 영향을 주지 않았다. 누락 하위 주제는 m02 human-in-the-loop(이전 측정과 동일), m05 long-term memory(신규)이며, 이전에 누락되던 m07 fallbacks는 재작성 3회 후 재검색으로 보완되었다.
- 롤백 전략: classify 프롬프트와 `searchQuery` 설명을 수정 전 문구로 되돌린다. 코드 경로 변경이 없으므로 프롬프트 변경만으로 복원된다.
