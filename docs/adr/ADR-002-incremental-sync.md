# ADR-002: 문서 갱신은 청크 본문 비교로 바뀐 페이지만 재임베딩

- **작성자**: 김아진
- **영향 범위**: Data
- **태그**: 비용 / 유지보수
- **관련 ADR**: ADR-001
- **링크**:

## 1) 배경 (Context)

- **문제**: 데이터 소스인 LangChain 문서는 계속 갱신되고, 청킹 파라미터를 바꿔 볼 때마다 재임베딩도 다시 해야 한다. 그런데 INSERT만 하는 단순한 방식은 재실행 시 청크가 중복되고, 문서에서 사라진 페이지가 DB에 남아 검색 결과에 섞인다.
- **제약**
    - `embed_user`는 SELECT / INSERT / DELETE만 가능하다. UPDATE가 없어서 upsert(`ON CONFLICT DO UPDATE`)는 쓸 수 없고, "삭제 후 삽입"으로만 교체할 수 있다.
    - Gemini 임베딩 무료 티어에는 한도가 있어 전체 약 3천 청크를 매번 다시 임베딩하기 부담스럽다. 결정 당시에는 분당 토큰 한도(실측 약 2~3만 토큰)만 알았는데, 첫 실행에서 일일 한도(실측 약 1,000건, 배치 안의 항목 1개 = 1건)도 확인됐다. 그래서 전체 재임베딩은 하루 안에 끝나지 않는다.
- **목표**: 추가·변경·삭제가 모두 DB에 반영되고, 한도 등으로 중간에 멈춰도 재실행하면 이어서 진행될 것
- **비목표**: 자동(주기적) 갱신

## 2) 고려한 선택지 (Options)

- 옵션 A: 매번 전체 재구축 (전부 삭제 후 재삽입, 단일 트랜잭션)
    - 장점: 가장 단순, 모든 경우 처리
    - 단점/리스크: 한 페이지만 바뀌어도 일일 한도를 넘겨 하루 안에 끝나지 않음. 중간 실패 시 처음부터 다시
- 옵션 B: 페이지별 청크 본문을 DB와 비교해 바뀐 페이지만 교체
    - 장점: 스키마 변경 없음(`source_url`, `content`만 사용), 변경분만 임베딩, 페이지 단위로 커밋되어 실패 후 재실행 시 이어서 진행
    - 단점/리스크: 청킹 결과가 결정적(deterministic)이어야 함
- 옵션 C: 페이지 `content_hash` 컬럼 추가 후 해시 비교
    - 장점: 비교가 가벼움
    - 단점/리스크: 스키마 변경, 청킹 파라미터만 바뀐 경우를 감지 못함

## 3) 결정 (Decision)

- 최종 선택: 옵션 B
- 결정 이유(Trade-off): 비교 대상이 "임베딩에 실제로 들어간 텍스트"라서 문서 변경과 청킹 방식 변경을 모두 같은 로직으로 감지한다(청킹을 바꾸면 자연스럽게 전체 재구축). 비교용으로 전체 `content`(약 4MB)를 읽어오는 비용은 3천 행 규모에서 무시할 수준.

## 4) 결과/영향 (Consequences)

- 긍정적 영향: 재실행이 항상 안전 (`pnpm --filter scripts embed`). 한도에 걸려 중단돼도 다음 실행이 이어서 처리.
- 부정적 영향/부채:
    - 페이지 사이에서 중단되면 일부 페이지만 신버전인 상태가 잠시 존재 (페이지 내부는 트랜잭션으로 일관)
    - 페이지 내 청크 하나만 바뀌어도 그 페이지 전체를 재임베딩
- 추후 작업(TODO): 필요해지면 GitHub Actions cron으로 crawl → chunk → embed 자동화.

## 5) 검증/롤백 (Validation / Rollback)

- 검증 방법: 같은 데이터로 재실행 시 `0 new/changed` 출력, `chunk.ts` 2회 실행 결과 해시 동일 확인.
- 롤백 전략: `embed.ts`를 전체 삭제 후 재삽입 방식으로 교체 (옵션 A).
