# ADR-010: 답변 피드백은 체크포인트 계정이 소유한 별도 스키마에 저장한다

## 메타

- **ADR ID**: ADR-010
- **상태**: 승인
- **날짜**: 2026-10-18
- **작성자**: 김아진
- **영향 범위**: Backend / Data / Security
- **태그**: 보안 / 유지보수
- **관련 ADR**: ADR-005
- **링크**: `apps/web/src/lib/feedback.ts`, `apps/web/src/app/api/feedback/route.ts`, `docs/schema.md`

---

## 1) 배경 (Context)

- **문제**: 답변마다 👍/👎와 사유를 받아 저장해야 한다. 👎 답변은 평가셋 후보로 쓰며, 이때 필요한 질문·검색어·출처는 대화 체크포인트에 이미 있으므로 피드백에는 체크포인트 식별자(`thread_id`, `checkpoint_id`)만 저장한다.
- **제약**
    - DB 계정은 용도별로 분리되어 있다. 문서 테이블은 `embed_user`(쓰기)·`readonly_user`(읽기)만 접근하고, `checkpoint_user`는 자기 소유인 `langgraph` 스키마만 접근한다 (ADR-005, `docs/schema.md`).
    - 피드백 API는 로그인 없는 공개 엔드포인트이므로, 존재하는 체크포인트에 대해서만 저장해야 한다. 따라서 피드백을 쓰는 계정은 `langgraph.checkpoints`를 읽을 수 있어야 한다.
    - `langgraph` 스키마의 테이블은 `@langchain/langgraph-checkpoint-postgres`의 마이그레이션이 관리한다.
    - Vercel 함수마다 커넥션 풀이 생기며, Neon 무료 플랜의 연결 수를 공유한다.
- **목표**: 문서 테이블 권한 분리를 유지하면서 체크포인트 존재 확인과 피드백 저장을 처리할 것
- **비목표**: 사용자 식별, 중복 투표 방지 (로그인이 없는 데모)

## 2) 고려한 선택지 (Options)

- 옵션 A: `checkpoint_user`가 소유한 별도 `feedback` 스키마
    - 장점: 체크포인트 존재 확인과 저장을 같은 연결·같은 SQL 문으로 처리. 환경 변수와 커넥션 풀이 늘지 않음. 패키지가 관리하는 스키마와 분리됨
    - 단점/리스크: 체크포인트 계정의 권한 범위가 피드백까지 넓어짐
- 옵션 B: 새 `feedback_user` 계정 (자기 스키마 + `langgraph.checkpoints` 읽기)
    - 장점: 권한이 가장 좁음
    - 단점/리스크: Vercel 환경 변수와 커넥션 풀이 하나씩 늘어남. 패키지 마이그레이션으로 체크포인트 테이블이 다시 만들어지면 읽기 권한을 다시 부여해야 함
- 옵션 C: `langgraph` 스키마에 테이블 추가
    - 장점: 설정이 가장 단순
    - 단점/리스크: 패키지가 관리하는 스키마에 직접 만든 테이블이 섞여, 마이그레이션·정리 작업 시 구분이 어려움

## 3) 결정 (Decision)

- 최종 선택: 옵션 A
- 결정 이유(Trade-off): 피드백은 체크포인트 없이는 쓸모가 없는 데이터로 대화 데이터와 수명이 같으므로, 같은 계정이 관리해도 권한 분리의 목적(문서 테이블 보호)은 유지된다. 옵션 B의 추가 분리는 운영 부담(환경 변수, 연결 수, 마이그레이션 후 재부여)에 비해 얻는 것이 작다. 옵션 C는 패키지 관리 영역과 섞이는 문제가 있다.

## 4) 결과/영향 (Consequences)

- 긍정적 영향: 체크포인트 커넥션 풀을 공유하며, 존재 확인과 저장을 `INSERT ... SELECT ... WHERE EXISTS` 한 문장으로 처리한다. 스키마 생성은 체크포인트 테이블과 같은 절차(DB CREATE 권한 임시 부여 → 생성 → 회수)를 따른다.
- 부정적 영향/부채
    - 체크포인트 테이블은 패키지가 관리하므로 외래 키를 두지 않았다. 대화를 지우는 `cleanup-threads`가 피드백도 함께 지워야 한다.
    - 공개 엔드포인트라 같은 답변에 대한 반복 제출은 마지막 값으로 덮어쓴다. 여러 사용자의 의견을 구분하지 않는다.
- 추후 작업(TODO): 👎 수집량이 쌓이면 `feedback-export`로 평가셋을 보강한다.

## 5) 검증/롤백 (Validation / Rollback)

- 검증 방법: 존재하지 않는 체크포인트 id로 저장하면 404가 반환되고 행이 생기지 않는지, 같은 답변에 다시 저장하면 1건이 갱신되는지, 새로고침 후 저장된 선택이 표시되는지 확인한다.
- 롤백 전략: `DROP SCHEMA feedback CASCADE`로 제거하고 화면의 피드백 버튼을 숨긴다. 대화 체크포인트에는 영향이 없다.
